# KshetraAI — Priority Engine Contract (V1)

---

# 1. Objective

The purpose of this contract is to define the implementation boundaries, responsibilities, and engineering rules for the Dynamic Prioritization Engine.

The Priority Engine is responsible for:

```text
Ranking farmers, retailers, and distributors
using weighted multi-signal operational scoring.
```

This engine determines:

```text
Who should be visited first,
and why.
```

It is one of the core intelligence engines of KshetraAI.

---

# 2. Module Identity

| Property | Value |
|---|---|
| Module Name | Dynamic Prioritization Engine |
| Layer | Core Intelligence Layer |
| Primary Responsibility | Priority ranking |
| Upstream Dependency | Feature Builder |
| Downstream Consumers | Contextual Engine, Dashboard, APIs |
| Architecture Criticality | High |

---

# 3. Core Philosophy

The Priority Engine should remain:

- deterministic
- explainable
- weighted
- interpretable
- operationally realistic

The engine should NOT:

- generate next best actions
- infer crop diseases
- generate explanations
- detect anomalies
- recalibrate learning weights

Its responsibility is ONLY:

```text
Priority scoring and ranking.
```

---

# 4. Responsibilities

The Priority Engine IS responsible for:

- combining normalized feature scores
- applying component weights
- generating final priority scores
- classifying urgency levels
- ranking entities
- generating component-wise score breakdowns

---

# 5. Non-Responsibilities

The Priority Engine is NOT responsible for:

- contextual recommendations
- agronomic inference
- anomaly escalation
- recommendation confidence
- explanation generation
- learning/recalibration
- API formatting
- frontend rendering

These belong to downstream modules.

---

# 6. Core Scoring Philosophy

The engine uses:

```text
Weighted multi-component scoring.
```

Each major operational component contributes to the final priority score.

---

# 7. Primary Scoring Components

| Component | Purpose |
|---|---|
| Agronomic Urgency | Crop/pest/weather urgency |
| Sales Opportunity | Revenue potential |
| Inventory Need | Restocking urgency |
| Relationship Need | Engagement/follow-up need |
| Competitive Pressure | Market defense urgency |
| Travel Efficiency | Route practicality |

---

# 8. Example Weight Structure

Example V1 weights:

| Component | Weight |
|---|---|
| Agronomic Urgency | 30% |
| Sales Opportunity | 25% |
| Inventory Need | 20% |
| Relationship Need | 10% |
| Competitive Pressure | 10% |
| Travel Efficiency | 5% |

Weights should remain configurable.

# 12. Agronomic Urgency Calculation

The engine combines:

- weather_risk_score
- pest_disease_risk_score
- crop_stage_risk_score
- ndvi_stress_score

---

# Example Logic

```text
High rainfall
+
High humidity
+
Pest alert active
+
Cotton flowering stage
→ higher agronomic urgency
```

---

# 13. Sales Opportunity Calculation

The engine combines:

- historical_sales_score
- seasonal_product_relevance
- purchase_history_score
- sales_opportunity_score

---

# Example Logic

```text
Strong fungicide demand
+
Peak seasonal relevance
→ higher sales opportunity
```

---

---

# 21. Deterministic Scoring Rule

The engine MUST remain:

```text
Fully deterministic.
```

Given identical inputs:

```text
priority outputs must remain identical.
```

Avoid:

- randomness
- hidden state
- non-configurable dynamic weighting

---

# 22. Explainability Preservation Rule

The engine MUST preserve:

- component score visibility
- traceable scoring
- interpretable weights
- score transparency

Avoid:

```text
opaque black-box scoring
```

---

# 23. Weight Configuration Rule

Weights should remain configurable.

Preferred:

```text
backend/config/priority_weights.yaml
```

Avoid:

```text
hardcoded scattered weights
```

---

# 24. Logging Requirements

The engine should log:

- entity scores
- component breakdowns
- ranking generation
- invalid scoring cases

Example:

```text
INFO:
Generated priority score 83.7 for ENT001
```

---

# 25. Error Handling Rules

Preferred:

```text
Explicit operational errors.
```

Example:

```text
ERROR:
Missing inventory_need_score for ENT004
```

Avoid silent failure.

---

# 26. Ranking Rules

The engine should:

- rank descending by priority
- preserve stable sorting
- support tie-breaking logic

Suggested tie-break priority:

```text
Higher agronomic urgency
        ↓
Higher sales opportunity
        ↓
Lower travel penalty
```

---

# 27. Schema Stability Rule

The engine MUST preserve:

- output schema
- score naming conventions
- component naming

The AI MUST NOT:

- rename output fields
- change score ranges
- alter classification labels silently

---

# 28. API Independence Rule

The engine should remain:

```text
pure intelligence logic.
```

The engine MUST NOT contain:

- API route logic
- frontend formatting
- HTTP handling
- UI rendering logic

---

# 29. Allowed Dependencies

Allowed:

```text
pandas
numpy
yaml
typing
dataclasses
```

---

# 30. Forbidden Dependencies

Avoid:

```text
heavy ML frameworks
distributed orchestration
LLM-based scoring
```

unless explicitly requested later.

---

# 31. Testing Requirements

The engine should be testable for:

- deterministic scoring
- ranking correctness
- weight application
- tie-breaking
- classification logic
- component breakdown integrity

---

# 32. Anti-Drift Rules

The AI MUST NOT:

- generate recommendations
- infer fungal disease
- detect anomalies
- generate explanations
- recalibrate weights automatically

The engine should remain:

```text
Pure weighted prioritization intelligence.
```
